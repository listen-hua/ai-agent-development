一、先建立整体认知

这个项目不是简单的聊天机器人，而是四类系统的组合：企业身份与权限、制度知识库与 RAG、飞书 H5 与机器人、可靠提醒与通知。

用户入口飞书 H5、普通浏览器、机器人私聊、群内 @ 机器人。
业务服务Go API 负责身份、对话、知识库、配置、通知与飞书长连接。
数据与 AIPostgreSQL、pgvector、MinIO、Tika、ClamAV 和阿里云百炼。
后台任务独立 Go Worker 调度提醒、处理重试、幂等和 90 天历史清理。
员工 → 飞书 H5 / 机器人 → Nginx / 长连接 → Go API → 权限过滤 → 检索与模型 → SSE / 飞书卡片
项目采用“模块化单体 + 独立 Worker”。它保留了简单部署和本地事务，又通过清晰模块边界为未来拆分服务留出空间。

三、Vue 3、TypeScript 与前端架构

Vue 3 解决什么问题

聊天页面需要处理消息追加、生成状态、引用到达、提醒确认、会话切换等大量响应式状态。Vue 的 ref、computed 和 Composition API 能把这些状态组织成可复用用例。

项目按职责拆分：路由页面负责组合，组件负责展示与交互，composable 负责业务状态，service 负责 HTTP/SSE，Pinia 只保存跨页面身份状态。

views        路由级组合
components   聊天、提醒、知识库等功能组件
composables  页面用例与异步状态
services     HTTP DTO、上传和 SSE
stores       当前用户、角色、登录状态
types        前后端共享概念的 TypeScript 类型

为什么选择 TypeScript

项目包含用户角色、文档版本、ACL、提醒状态、SSE 事件和引用等复杂类型。TypeScript 能在构建阶段发现字段拼写、可空值和状态分支错误，显著降低前后端联调风险。

为什么是 Pinia，而不是所有状态都全局化

跨页面共享的身份信息进入 Pinia；聊天状态放在 useChat；弹窗和表单放在组件内部。这避免了全局 Store 变成难以维护的“大杂烩”。

为什么使用 Element Plus

后台包含大量表格、上传、日期、对话框和表单验证，使用成熟组件库比自研更可靠。代价是主包较大，后续可通过按需导入和手动分包优化。

四、为什么后端选择 Go

系统多数工作是网络 I/O：调用模型、访问飞书、查询数据库、发送 SSE、上传 MinIO 和调用 Tika。Go 的 goroutine、context.Context、静态编译和较低资源占用非常适合这类长期运行服务。

Go 的优势

单二进制、启动快、并发模型简单、内存可控、部署轻、标准库完整。

对应代价

业务开发没有 Java 框架那么丰富，SQL 和错误处理更显式，需要团队保持工程规范。

为什么不是 Node.js

Node.js 适合快速原型，但 Worker、文件处理、长连接和多类后台任务在 Go 中更容易保持资源稳定。若团队全部是 TypeScript 工程师、目标只是快速验证，NestJS 也会是合理选择。

为什么不是 Spring Boot

Spring Boot 更适合大型组织和复杂中台，但当前首期规模下内存、启动、配置和部署成本偏高。未来若行政场景扩展成大型流程平台，可以重新评估。

为什么直接使用 net/http

Go 新版本标准路由已支持方法和路径参数，当前接口复杂度不要求 Gin。减少框架依赖意味着行为更透明；若未来需要 OpenAPI 自动生成、复杂绑定和大量中间件，再引入框架更合适。

五、模块化单体为什么优于首期微服务

部署上是一个代码库，但代码按领域分为 domain、service、store、model、integration、httpapi 等模块。API 和 Worker 使用同一套领域与仓储代码，但编译成不同入口。

如果首期直接拆成身份、知识库、对话、通知、提醒、飞书网关六个服务，就会立刻引入服务发现、分布式事务、消息一致性、多套部署和链路追踪，而用户规模尚未带来对应收益。

微服务不是“更先进”的同义词。边界清晰的模块化单体通常是中小团队构建复杂业务的最佳起点。

六、Repository 模式、依赖倒置与直接 SQL

Service 不直接调用 PostgreSQL，而依赖 Repository 接口。项目提供内存实现和 PostgreSQL 实现，因此本地测试不必依赖数据库，业务逻辑也不会和 SQL 混在一起。

type Repository interface {
    GetUser(...)
    SearchChunks(...)
    CreateReminderAction(...)
    ClaimReminderDeliveries(...)
}

项目没有使用 ORM，而是使用 pgx 和原生 SQL。原因是 pgvector 距离、JSONB ACL、全文检索、HNSW 和 FOR UPDATE SKIP LOCKED 都需要精确控制 SQL。ORM 会隐藏细节并增加调优难度。

直接 SQL 的代价是扫描字段和迁移需要人工维护，因此复杂查询应通过数据库集成测试保护。

七、PostgreSQL + pgvector

PostgreSQL 同时保存用户、角色、文档、版本、ACL、切片、向量、会话、配置、通知、提醒、工作日历、审计和事件幂等记录。

为什么不是独立向量数据库

当前目标规模不超过约 10,000 份文档、1,000 名员工和 30 路并发。pgvector 可以让文档状态、ACL 和向量处于同一事务和同一 SQL 中，避免向量库与业务库双写不一致。

为什么不是外部云向量库

公司制度和元数据具有数据边界要求。自建 PostgreSQL 可以减少数据出域、供应商锁定和删除审计复杂度。

什么时候应该迁移

切片进入千万级、高并发检索影响事务、需要复杂分片或多模态向量大量增长时，再考虑 Milvus、Qdrant 或 OpenSearch。

八、RAG 的完整工作原理

上传 / 飞书同步 → 查毒 → 解析 → SHA-256 → MinIO → 切片 → Embedding → 草稿 → 发布 → 检索 → Rerank → 生成与引用

原文件、哈希与版本

原文件保存在 MinIO，数据库只保存对象键。SHA-256 根据内容判断是否变化：哈希相同说明内容未变，哈希不同则创建新草稿版本。新版本必须由管理员发布后才能进入普通问答。

为什么要切片

模型上下文有限，整份制度不能每次全部发送。当前按约 900 个 Unicode 字符切片，并保留约 120 字符重叠，避免完整规则刚好被截断。更高级的版本应按标题、段落和表格结构切分。

Embedding 与 HNSW

Embedding 将文本转换为 1024 维向量，让“年假怎么申请”和“带薪年休假流程”即使字面不同也能按语义匹配。HNSW 是近似最近邻索引，用极小的精度代价换取更快检索。

为什么不能只有向量检索

金额、制度编号、部门名和专有词更适合关键词检索。当前数据库排序大致为：

综合分数 = 0.7 × 向量相似度 + 0.3 × PostgreSQL 全文分数

随后应用层用中文词项和双字组合再次匹配，再调用 Rerank。当前是“加权混合检索”，不是严格 RRF；后续更稳健的实现应把向量 Top-K 和关键词 Top-K 分开召回，再用 RRF 按排名融合。

Rerank 的意义

Embedding 负责从大量切片快速召回，Rerank 同时阅读问题和候选片段，负责更精确排序。不能让 Rerank 直接扫描全部知识库，因为成本和延迟都太高。

权限先于模型

正确链路是“权限过滤 → 检索 → Rerank → 模型”。受限内容不能先进入模型再要求模型保密。当前在 SQL 和 Go 应用层执行双重 ACL 检查。

Prompt Injection 与引用

制度内容被标记为不可信资料，模型不得执行文档里的指令。但 Prompt 不是绝对安全边界，真正的边界仍然是 ACL、最小上下文、工具权限和审计。

引用对象来自本次授权召回结果，包含制度名、版本、章节、页码、摘录和来源链接。当前尚未做到逐结论引用覆盖校验，若目标是 100% 引用覆盖，还需解析答案引用编号、拒绝无效编号并检测冲突证据。

九、阿里云百炼与模型分工

任务模型原因

业务层只依赖统一 Provider 接口：Generate、StreamGenerate、Embed、Rerank。因此未来可以添加本地模型或其他 OpenAI 兼容服务，不需要重写知识库。

制度回答明确设置 enable_search=false，避免模型联网后混入非公司信息。

十、为什么聊天使用 SSE

SSE 适合服务端到浏览器的单向持续推送。当前发送 status、delta、citation、done 和 error 事件。

相对 WebSocket，SSE 基于普通 HTTP、调试简单、Nginx 支持成熟，而且 AI Token 流不需要高频双向通信。

前端另外使用文本流控制器平滑展示 chunk，因为模型一次返回的可能是一句话而不是单个字。

当前“停止生成”主要停止浏览器接收和本地动画，尚未真正取消阿里云上游请求。后续应维护 run_id 到 cancel function 的映射，并增加服务端取消接口。

十一、飞书免登、内部 UUID 与 HttpOnly 会话

H5 调用 tt.requestAuthCode → 一次性 code → Go API → 飞书换取身份 → 内部 User → HttpOnly Cookie

App Secret 永远只保存在服务端。浏览器得到的飞书 code 是一次性的，后端换取 open_id 后映射到内部 UUID。

业务实体使用内部 UUID，而不是直接把飞书 open_id 当主键，可以减少外部平台绑定，也便于未来接入其他协同平台。

会话 Cookie 使用 HMAC-SHA256 签名，配置 HttpOnly、SameSite=Lax，并在生产环境启用 Secure。相比 localStorage JWT，JavaScript 无法直接读取它，降低 XSS 窃取风险。

生产环境还应补充 Origin/Referer 校验、CSRF 防护、强制会话撤销和 Secret 轮换。

十二、RBAC 与文档 ACL/ABAC

RBAC：控制能做什么

角色包括员工、知识管理员、通知管理员、审计员和超级管理员。管理员角色必须显式授予，不根据“经理”“主管”等职务自动推导，因为职位不等于系统权限。

ACL/ABAC：控制能看什么

文档可根据部门、职务、职级、序列、人员类型、指定用户和后台角色限制。单个规则组内部为 AND，多个规则组之间为 OR。

（财务部 AND 会计）
OR
（指定用户张三）

RBAC 控制后台操作，ACL 控制数据可见范围，两者不能互相替代。

十三、为什么飞书事件使用 WebSocket 长连接

长连接不需要开发电脑具备公网 HTTPS 地址，官方 SDK 负责连接和重连，适合开发环境和当前部署方式。HTTP 回调则需要公网网关、证书、验签和解密，接入成本更高。

项目通过数据库中的 event_id 幂等记录防止飞书重复事件造成重复回复或重复任务。

未来多 API 副本运行时仍必须保留数据库幂等，不能依赖单进程内存去重。

十四、个人提醒系统的核心知识

规则与 AI 混合解析

时间属于确定性业务。系统优先使用可测试的中文规则解析，无法处理时再调用 qwen-flash JSON Mode，并由服务端校验结构。相比全 AI 更稳定、便宜；相比全正则又能覆盖更多自然表达。

Human-in-the-loop 二次确认

自然语言解析后不会立即创建提醒，而是生成 30 分钟有效的 Action Draft。只有用户确认才真正提交。这是“Prepare → Commit”的两阶段命令模式，适合所有会影响外部世界的 AI 操作。

为什么不用系统 Cron

个人提醒可以随时创建、修改、暂停和删除，还涉及工作日、失败重试和发送记录。操作系统 Cron 不适合管理大量动态用户任务，因此系统使用数据库中的 next_fire_at 调度。

SKIP LOCKED、租约与幂等

Worker 通过 FOR UPDATE SKIP LOCKED 竞争任务。一个 Worker 锁住任务后，其他 Worker 跳过；若进程崩溃，locked_until 到期后可重新领取。

投递表对 (reminder_id, scheduled_for) 和 idempotency_key 建立唯一约束，避免重启、超时和重复轮询造成重复投递。

补发窗口与工作日历

延迟不超过 30 分钟会补发并标记延迟，超过则标记 missed，避免第二天发送已经失效的提醒。工作日默认周一至周五，再由公司节假日和调休日历覆盖。

十五、MinIO、Tika 与 ClamAV

MinIO

MinIO 是自建 S3 兼容对象存储。与本地目录相比，它适合容器、多实例、统一备份和未来迁移阿里云 OSS；与数据库 BLOB 相比，不会让业务库因大文件快速膨胀。

Apache Tika

Tika 用统一接口解析 PDF、DOCX、PPTX、XLSX、HTML 和文本，避免为每种格式维护独立解析库。缺点是复杂版面、表格、页码和标题层级可能丢失。

ClamAV

文件在解析与存储前查毒，防止恶意 Office、病毒附件和解析器攻击。当前 OCR 仅预留接口，Compose 尚未部署 PaddleOCR，因此纯扫描 PDF 仍可能无法提取文本。

十六、Docker Compose 与 Nginx

Compose 管理 PostgreSQL、Redis、MinIO、Tika、ClamAV、API、Worker 和 Web。对于 1～2 台服务器，它比 Kubernetes 更容易部署、备份和排错。

当系统需要多机高可用、自动扩缩容、滚动发布和统一集群治理时，再迁移 Kubernetes。

Nginx 同时提供静态页面、SPA 路由回退、API 反向代理、同源 Cookie 和 SSE 代理。API 8080 不直接暴露给宿主机，减少攻击面。

当前 Nginx 可能在 API 容器重建后保留旧容器 IP，需要重启 Web 容器。生产环境应使用动态 DNS 解析或稳定服务发现配置。

十七、Redis 当前到底做了什么

Redis 已在 Compose 中部署并开启 AOF，但当前 Go 代码还没有真正创建 Redis 客户端。提醒队列实际使用 PostgreSQL 的投递表、租约、唯一约束和 SKIP LOCKED。

当前规模下 PostgreSQL 队列的优势是任务与业务状态处于同一个事务系统，避免 Redis 与数据库双写不一致。

后续 Redis 可以承担飞书 Token 缓存、分布式限流、短期 SSE 状态、高频队列和分布式锁。

十八、配置与文档为什么必须版本化

模型、Prompt 和检索参数采用 draft → published → archived；文档也采用草稿、发布和归档生命周期。

  • 修改不会立即污染线上。
  • 可以测试和评测后再发布。
  • 能够追踪某次回答使用的配置。
  • 发生问题时可以回滚。
  • 便于审计模型和制度的变化。

二十、当前实现与原始规划的差异

  • 混合检索是加权分数，不是严格 RRF。
  • 中文全文索引使用 PostgreSQL simple 配置和应用层双字匹配，不是真正中文分词。
  • OCR 仅预留接口，尚未部署 PaddleOCR。
  • Redis 已部署，但目前没有进入实际业务链路。
  • 文档切片仍是固定长度，标题、表格和页码结构保留有限。
  • SSE 停止按钮尚未真正取消阿里云上游请求。
  • 引用来自授权召回，但尚未做逐结论引用覆盖校验。
  • 飞书资料源支持手动同步，当前 Worker 主要执行提醒；15 分钟自动同步仍需加入调度。
  • Docker initdb 迁移只对新数据卷自动执行，已有数据库要手工运行 SQL。
建议尽快引入 goose 或 golang-migrate，把迁移纳入发布流程；随后优先加强中文检索、结构化切片、引用验证和真正的上游取消。

二十一、最值得掌握的核心思想

  1. 权限必须先于检索，不能依赖模型替系统保密。
  2. RAG 不是训练模型，而是先检索证据再生成回答。
  3. 向量解决语义，关键词解决精确匹配，Rerank 负责精排。
  4. AI 操作外部世界时必须加入人工确认和幂等机制。
  5. RBAC 控制操作权限，ACL/ABAC 控制数据可见范围。
  6. 动态个人提醒适合持久化调度，不适合逐条系统 Cron。
  7. PostgreSQL 可同时承担业务库、中小规模向量库和可靠队列。
  8. 模块化单体适合首期，微服务不是先进程度的标志。
  9. 模型可以替换，权限、版本、审计和可靠性才是长期资产。
  10. 企业 AI 的难点不只是调用模型，而是数据生命周期和错误边界。

这套架构的长期价值在于：模型供应商可以变化，但身份、权限、知识治理、引用、提醒调度和审计不必推倒重来。
