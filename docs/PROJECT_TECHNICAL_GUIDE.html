一、项目定位与边界

这个项目已经不是单一的“制度聊天机器人”，而是一套嵌入飞书的公司内部行政 AI 平台。它同时处理身份、组织权限、制度知识、行政任务、可靠消息投递、会议室资源和图片生产。

制度助手上传或同步制度，按员工权限检索，生成带版本和原文引用的回答。
行政执行个人提醒、工作日历、通知中心、会议室预约、取消、改期和会后归还提醒。
飞书集成H5 免登、通讯录、云空间、Wiki、机器人长连接、消息卡片和日历接口。
AI 生图多中转站、多模型、项目权限、异步生成、参考图和持久化无限画布。
最关键的认识：大模型只负责“理解和生成”，权限判断、时间校验、资源占用、审批确认、幂等与补偿必须由确定性代码负责。这样才能把概率性的 AI 放进可审计的企业流程。

当前明确不做的事

系统没有把 AI 设成拥有无限工具权限的自主 Agent；不会让模型自行扩大收件人、绕过确认、读取未授权制度或直接猜测重名员工。AI 生图的“工作流”也只是入口占位，尚未实现多人协同节点编排。

二、整体架构：模块化单体 + 独立 Worker

H5 链路：飞书工作台 → Nginx → Vue 单页应用 → Go API → PostgreSQL / MinIO / Redis / 阿里云或图片中转站
机器人链路：飞书 WebSocket 长连接 → Go 事件处理 → 数据库任务或对话运行 → 飞书消息卡片
异步链路：Go Worker → 领取到期任务 → 外部 API → 幂等记录、重试或人工告警

为什么采用模块化单体

当前规模预期不超过约 1,000 名员工、10,000 份文档和 30 路峰值问答。此时最昂贵的通常是外部模型调用和文档处理，不是单体进程本身。将身份、知识库、对话、提醒、通知、会议和生图放在一个 Go 代码库中，可以共享领域类型、事务、权限和审计规则，部署也更简单。

选型模块化单体，而不是一开始拆微服务

当前方案的收益

跨模块事务简单；本地开发容易；接口和 DTO 不必跨仓库同步；两台服务器即可部署；出现问题时日志链路较短。

没有选微服务的原因

微服务会提前引入服务发现、分布式追踪、跨服务鉴权、消息一致性和版本治理，而首期业务量不足以抵消这些成本。

项目仍把 API 与 Worker 分成两个进程：API 追求低延迟，Worker 负责同步、解析、提醒、会议室会后消息和生图等耗时任务。两者共享代码和数据库，但故障域与资源占用相对隔离。

四、前端架构：一个 Vue 应用承载员工端和管理端

同一个 Vue SPA 提供 /chat、/reminders、/image-agent 和多个 /admin/* 页面。路由懒加载减少飞书 WebView 首次下载体积；Pinia 保存跨页面的身份和会话状态；复杂页面继续拆成 feature component、composable、service 与 type。

Router

根据身份判断是否登录，根据统一权限键决定能否进入管理路由；未知路由进入独立 404 页面。

Service 层

统一封装 REST 与 SSE，页面不直接拼接底层请求细节，避免 DTO 散落在组件里。

组件拆分

聊天消息、引用抽屉、ACL 编辑、会议卡片、富文本编辑器和画布节点均独立维护。

为什么选 Vue 3 + TypeScript

行政后台的复杂度主要来自表格、筛选、抽屉、表单、角色控制和多个异步状态，而不是极端 SEO 或跨端原生渲染。Vue 的响应式状态和单文件组件对此很合适；TypeScript 可以在编译阶段发现“后端新增字段但前端仍按旧结构访问”等问题。

没有选 React 的原因

React 同样能完成需求，但本项目不存在必须依赖 React 生态的能力；切换只会增加团队学习与迁移成本，不会改变系统核心安全性。

没有选微前端的原因

员工端和后台共享身份、设计系统与领域类型。当前团队和页面数量不足以支撑微前端带来的运行时隔离、依赖重复和发布协调成本。

为什么使用 Element Plus，而不是全部自研

管理系统的价值在业务规则，不在重复实现日期选择器、表格、分页、上传和无障碍键盘行为。Element Plus 提供可靠基础控件；项目再通过自定义布局和样式建立自己的视觉语言。无限画布是特殊交互，因此没有勉强使用后台组件库，而是单独采用 Vue Flow。

五、Go 后端：薄 HTTP 层、业务 Service、Repository 与 Integration

HTTP Handler → 参数和身份 → Service → 业务规则 → Repository / Integration → PostgreSQL、飞书、模型与对象存储

HTTP 层只处理输入输出与中间件；Service 负责“能不能做、先做什么、失败如何补偿”；Repository 隔离 PostgreSQL；Integration 隔离飞书、阿里云、Tika、MinIO 和中转站协议。

为什么使用标准库 net/http

Go 新版路由已经支持方法和路径参数，项目接口规模也没有大到需要重型 Web 框架。标准库依赖少、行为透明，SSE 与中间件足够实现。若以后需要自动 OpenAPI 生成、复杂参数校验或大量插件，再评估 Echo、Gin 或代码生成框架更合理。

为什么 API 和 Worker 分进程

  • 文档解析、生图和外部消息发送可能持续数秒到数分钟，不应占住请求生命周期。
  • Worker 可以独立重启和扩容，外部模型拥堵不会直接拖垮登录与查询接口。
  • 任务状态先入 PostgreSQL，页面刷新或进程重启后仍可恢复。
“异步”不是简单地开一个 goroutine。重要任务必须先持久化，再由 Worker 领取；否则 API 进程重启会让内存中的提醒、生图或通知永久丢失。

六、数据基础设施：一套存储承担不同职责

PostgreSQL：系统事实来源

用户、权限策略、IAM快照、组织属性、会话、文档版本、切片、配置、通知、提醒、会议预约、生图任务、画布和审计都以 PostgreSQL 为准。JSONB 用于配置、ACL 和扩展字段；事务用于版本发布、任务领取和状态流转；FOR UPDATE SKIP LOCKED 让多个 Worker 能并发领取任务而不重复处理。

pgvector：向量与权限共库

向量存放在制度切片行中。当前实现将向量相似度和 PostgreSQL 全文排名做加权，再在应用层按中文词命中做一次筛选排序，最后调用 Rerank。它并非独立向量数据库，也不是严格 RRF 实现。

选型pgvector，而不是 Milvus、Qdrant 或 Elasticsearch

为什么现在适合

10,000 份文档规模下，共库可以在同一查询中先过滤已发布版本和用户 ACL，再计算相似度，避免向量系统返回无权限结果。

为什么暂不拆

独立向量库会增加双写、版本一致性、权限过滤、备份和运维。只有向量达到千万级、检索 QPS 很高或需要专用索引能力时收益才明显。

MinIO：大文件和图片

数据库只保存对象键、元数据、哈希和权限关系，二进制内容放在 MinIO。相比本地目录，它更适合容器重建和后续多实例；相比直接把 BLOB 塞进 PostgreSQL，它不会让事务日志、备份和主库 IO 被大图片拖累。

Redis：只用于真正需要的短期分布式协调

当前明确使用 Redis 进行会议室时段锁：用带 TTL 的 SET NX 抢锁，并用校验锁值的 Lua 逻辑释放，防止误删别人的锁。提醒、通知和生图的持久任务领取则使用 PostgreSQL 行锁，因为这些任务必须可审计和可恢复。

七、飞书免密登录：身份由飞书证明，会话由本系统管理

飞书 H5 SDK 获取临时 code → 后端用 App ID/Secret 换用户身份 → 同步组织资料 → 签发 HttpOnly Cookie → /api/v1/me 返回当前用户

前端优先调用飞书客户端提供的授权能力，失败时按兼容路径尝试另一种授权码接口。后端不相信前端直接传来的 open_id，而是使用一次性 code 向飞书换取身份。登录成功后签发 12 小时会话 Cookie，并设置 HttpOnly、SameSite=Lax，生产环境启用 Secure。

为什么不把 Token 放 localStorage

localStorage 可被页面中的恶意脚本读取；HttpOnly Cookie 对 JavaScript 不可见，能降低 XSS 直接窃取会话的风险。Cookie 方案需要处理 CSRF 与 SameSite，但同源 H5 + API 的结构正适合这一模式。

超级管理员如何初始化

BOOTSTRAP_SUPER_ADMIN_OPEN_IDS 只用于冷启动。API 启动会为已存在用户本地允许全部八项权限；尚未登录的用户在首次登录时获得相同策略。完成首位管理员初始化后应移除该环境变量，再从“用户与权限”页面维护本地覆盖。

八、权限体系：RBAC 管功能，组织 ACL 管数据

RBAC：决定可以操作什么

IAM和微光本地策略使用同一组八个权限键，最终结果为(IAM ∪ 本地允许) − 本地拒绝。前端隐藏无权限菜单以改善体验，后端对每个接口再次校验最终权限。前端路由守卫不是安全边界，因为用户可以绕过页面直接调用 API。

组织 ACL：决定可以看到哪份制度或哪个项目

登录或组织事件同步后，本地用户保存飞书部门、职位、职级、序列、员工类型和人员 ID。ACL 规则支持这些维度。一个规则内部不同维度是 AND，同一维度多个值是 OR；多条规则之间是 OR。例如：

规则 A：部门 ∈ {财务部, 审计部} AND 职位 ∈ {会计}
规则 B：指定人员 ∈ {张三}
最终可见 = 规则 A 命中 OR 规则 B 命中

检索时先在 SQL 中过滤，再用领域对象的 ACL.Allows(user) 二次防御。超级管理员可以绕过文档 ACL用于治理，但普通员工无法通过猜文件名、引用 ID 或历史会话越权。

选型统一模块权限 + ABAC/ACL，而不是只用角色

为什么要混合

后台能力适合少量稳定权限键；制度可见范围经常按部门、职位或人员变化，仅靠模块权限会产生大量“财务会计制度读者”式权限。

为什么不实时依赖飞书文件权限

飞书源权限只表示应用能否读取源文件，不能直接等价为员工在 AI 中的可见范围；内部发布流程也需要独立、可审计的权限快照。

九、制度资料入库：从“不可信文件”到“可发布证据”

上传：文件 → 大小/MIME 校验 → ClamAV → MinIO → Tika → 切片 → Embedding → 草稿版本
飞书同步：资料源 Token → 递归 Drive/Wiki → 解析真实对象 → 下载/导出 → 哈希比对 → 新草稿版本
上线：管理员检查内容与 ACL → 发布新版本 → 旧版本下线 → 新会话立即检索新版本

上传与解析

普通文本和 Markdown 可直接读取；PDF、DOCX、PPTX、XLSX、HTML 等交给 Tika。上传前由 ClamAV 扫描，原文件通过对象键存入 MinIO，解析后的文本切片和向量写入 PostgreSQL。切片保留文档、版本、顺序、标题、页码和正文，为引用回溯提供结构。

为什么先查毒再解析

解析器面对的是外部输入，历史上 Office、PDF 和压缩格式都可能触发解析漏洞。先限制大小和类型，再查毒，最后交给 Tika，能缩小攻击面。ClamAV 不是万能沙箱，但比“直接让业务进程解析任何文件”更稳妥。

飞书云空间与 Wiki

资料源支持云空间文件夹和 Wiki 根节点。Wiki 页面先解析 obj_token 与 obj_type，再按 Docx、Sheet、Bitable 或普通文件读取/导出；递归遍历子节点。后台选择的部门来自飞书公司组织架构同步结果，而不是手工写死。

为什么同步后是“待发布”

同步只证明源文件发生变化，不证明内容、解析质量、生效日期和 ACL 已经正确。新版本先进入草稿，管理员确认后发布；发布新版本时旧版本下线。这避免飞书里一次误编辑立即污染所有员工问答。

增量与失权处理

系统按远程 Token 定位文档，以 SHA-256/版本校验识别未变化内容；Worker 周期性同步，也支持手动触发。源文件删除或应用失去读取权限时，文档停止参与检索，但审计历史不被直接物理删除。

当前边界：Compose 中没有独立 PaddleOCR 服务。扫描版 PDF 或纯图片制度的文字识别质量取决于 Tika 可提取内容；如扫描件占比高，应新增 OCR 阶段和人工抽检。

十、RAG 制度问答：回答必须来自本轮授权证据

  1. 问题独立化
    上下文引擎把“那试用期呢”改写成语义完整的问题。
  2. 强制 ACL
    用当前用户组织属性过滤已发布且有效的文档版本。
  3. 混合召回
    向量相似度解决语义表达差异，全文和词命中保留精确术语。
  4. Rerank
    对候选切片做更精细的查询—文档相关性排序。
  5. 证据预算
    只把高相关片段放入上下文，避免长文档淹没问题。
  6. 严格引用
    模型每个制度结论必须用 [数字] 指向本轮片段。
  7. 服务端验证
    引用越界、引用缺失或无证据时改为固定拒答。
  8. 审计反馈
    保存模型、引用、配置版本、Token 与赞踩结果。

为什么同时使用向量、关键词和 Rerank

只用关键词会漏掉“调休”和“补休”等语义近似表达；只用向量可能在制度编号、金额、专有名词上不够精确；直接把 200 个候选交给大模型成本过高。当前方案先低成本扩大召回，再用 Rerank 收敛到少量证据。

当前混合检索的真实实现

PostgreSQL 查询使用约 0.7 的向量相似度和 0.3 的全文排名组合，最多取一批候选；应用层再按分词命中数量排序并限制数量；随后调用阿里云 Rerank。它比纯向量稳定，但严格来说不是 Reciprocal Rank Fusion。若以后需要可解释地融合多个独立排序列表，可改为 RRF。

为什么不把所有制度直接放进 Prompt

上下文窗口有限、成本高，且无法对每一段执行可靠权限过滤。检索后只发送当前用户有权访问的 5～8 个高相关切片，可以降低泄露风险、延迟和幻觉。

Prompt 注入怎么处理

制度正文被标记为“不可信数据”，模型不得执行其中的指令；历史回答也只用于理解语境，不是制度证据。真正的安全边界仍在服务端：ACL 先过滤、引用只能指向本轮结果、无有效引用则拒答。

十一、多轮上下文引擎：记住任务，不把旧答案当事实

每轮对话不再只处理当前一句话。上下文引擎读取最近 12 条消息（约 6 轮）、滚动摘要和未完成任务状态，默认使用低成本 qwen-flash 以 JSON 形式输出意图、独立问题、任务字段和缺失字段。

{
  "intent": "meeting | reminder | policy_qa | conversation_control | out_of_scope",
  "standalone_query": "结合历史后完整表达的请求",
  "active_task": {
    "status": "collecting | active | awaiting_confirmation",
    "slots": {},
    "missing_slots": []
  }
}

为什么不把全部聊天历史直接塞给生成模型

  • 历史越长，Token 成本和首字延迟越高，模型对当前问题的注意力反而下降。
  • 旧回答可能已经过期或当时就有误，不能继续充当制度证据。
  • 提醒和会议预约需要结构化字段，不应依赖模型在长文本中隐式“记得”。

因此系统把上下文拆成“近期原文 + 摘要 + 任务槽位”。制度问答每轮重新检索，摘要只保存用户明确表达的事实、讨论主题和已确认工具结果。引用进入历史上下文前还会检查文档是否仍发布且当前用户仍有权限。

上下文预算

默认总输入约 12,000 Token：当前证据最多约 55%，近期对话和任务最多约 30%，摘要最多约 15%。安全提示和当前问题优先级最高。超过阈值时更新滚动摘要，但保留最近原文。

不同入口如何隔离

  • H5 以 conversation_id 为边界；新建会话得到干净上下文。
  • 机器人私聊按用户 + chat_id + agent_key 绑定；群聊还按用户隔离，其他群成员不会继承上下文。
  • 30 分钟无交互后机器人创建新上下文；“清除上下文”“重新开始”可主动重置。
  • 不同 Agent 使用不同 agent_key，行政助手内容不会传到生图 Agent。

为什么同一会话要串行处理

用户可能连续发送“帮我订会议室”和“今天下午三点”。如果两轮并发分析，第二轮可能在第一轮消息尚未入库时读取历史，导致字段丢失。会话级队列保证消息按到达顺序处理；数据库任务幂等再防止重复执行。

上下文模型失败时，完整且明确的单轮请求可以走确定性解析器；明显依赖历史的句子则要求用户完整重述，不能为了“体验顺滑”而猜时间、对象或执行动作。

十二、AI 流式回答：SSE 负责传输，前端负责平滑呈现

发送消息后，API 立即返回 run_id。前端用 EventSource 连接运行事件流，依次接收：

statusdeltacitationdoneerror

status 会告诉界面正在结合上下文、检索或生成；delta 是模型增量文本；citation 单独补充引用；done 给出最终落库消息。Nginx 对 /api/ 关闭代理缓冲，避免增量被攒成一大块后才发给浏览器。

选型SSE，而不是 WebSocket

SSE 正好匹配

浏览器端 AI 回答是服务端到客户端的单向事件流；自动重连和标准 HTTP 代理都较成熟。

WebSocket 没有额外收益

用户提问仍可走普通 POST。若为此维护双向连接，需要额外心跳、协议和重连状态，复杂度高于收益。

“一个字一个字”的视觉效果不能只靠 CSS；它来自服务端真实流式回调与前端增量追加。最终消息仍由服务端落库并校验引用，前端不能把未完成流当作最终事实。

十三、飞书机器人：长连接接事件，异步执行重任务

项目使用飞书官方 SDK 的 WebSocket 长连接接收消息、卡片点击、通讯录变化和会议室状态变化。无需将事件回调端点暴露到公网，也减少本地开发阶段的 HTTPS 穿透配置。

为什么长连接适合当前部署

应用主要运行在内网，出站连接通常比开放公网入站更容易；SDK 负责鉴权、心跳和事件分发。若未来多地域部署或企业网络不允许稳定长连接，才考虑公网 HTTP 回调加网关验签。

事件处理的可靠性

  • 每个飞书事件先写入 processed_events，唯一键保证重复投递不重复执行。
  • 消息事件尽快转入异步作业，避免阻塞飞书响应窗口。
  • 卡片按钮携带内部 action ID，但后端仍校验事件用户、任务归属、状态和过期时间。
  • 机器人回答附带 AppLink，复杂引用和操作可回到 H5 查看。
“收到一次事件”不等于“只会执行一次”。网络重试、SDK 重连和用户重复点击都会产生重复输入，因此幂等必须依赖数据库唯一约束和状态机，而不是内存布尔值。

十四、个人提醒：AI 解析自然语言，数据库保证准时与不重复

“工作日 11:50 提醒点外卖” → 解析内容/时间/重复规则 → 确认卡片 → Reminder → Worker 物化投递 → 飞书私聊

实现要点

  • 解析绝对日期、相对日期、上下午、单次/每天/工作日重复。
  • 信息不完整时保存任务槽位并追问；完整后先生成确认卡片，不立即创建正式提醒。
  • 工作日不是简单的周一到周五，后台工作日历可以覆盖节假日和调休。
  • Worker 先把规则物化为具体投递，再用 SKIP LOCKED 加租约领取。
  • 网络、429 和临时服务错误按退避策略重试；权限类错误进入永久失败。
  • 每次投递有幂等键，重复 Worker 不会重复发同一条提醒。

为什么不用系统内存定时器或 cron

内存定时器在容器重启后丢失，多个实例会重复触发；cron 擅长固定系统任务，不擅长数百名用户随时增删的动态规则。数据库状态机让提醒可暂停、取消、审计和恢复，Worker 只是执行者。

为什么要单独维护工作日历

中国节假日和调休无法用普通 weekday 规则正确表达。将特殊日期保存为工作/休息覆盖项，既能解释“为什么今天触发”，也能由行政修正，而无需修改代码。

十五、通知中心：人工审核的富文本群发

通知管理员可以选择个人或机器人已加入的大群，编辑 Markdown 风格正文，上传图片，设置计划时间，预览卡片并审批后发送。过去时间在前端限制的同时，后端也拒绝，防止绕过界面。

富文本如何映射到飞书卡片

后台编辑器只开放飞书卡片可稳定表达的格式。标题语法会在发送前规范化，正文转换为卡片 Markdown 元素，图片使用飞书上传后得到的 image_key。这样比直接发送 HTML 更可靠，因为飞书卡片并不执行任意 HTML，支持的 Markdown 也不是完整 CommonMark。

为什么限制图片和正文大小

前端体验、飞书卡片协议和消息接口都有边界。系统在服务端限制标题、正文和最多 9 张图片，防止生成无法发送的草稿。服务端校验是最终标准，不能只依赖编辑器。

审批、调度与投递结果

  • 草稿只有经过通知管理员审批才能进入发送流程。
  • AI 只负责润色正文，不拥有收件人和发送权限。
  • 发送前重新解析个人或群聊目标，发现机器人已退群则停止。
  • 计划任务由 Worker 使用数据库行锁领取；每个接收者记录消息 ID、状态、错误和尝试次数。
  • 幂等 UUID 会规范到飞书允许长度，避免长内部 ID 导致接口字段校验失败。
选型人工审批，而不是 AI 自主通知

为什么必须审核

群发消息影响面大，错误对象、时间或措辞会造成真实组织风险；管理员应看到最终卡片和人数后确认。

为什么不让模型决定收件人

自然语言模型可能误解部门、重名人员或历史语境。目标解析和权限必须由确定性目录数据完成。

十六、智能会议室预约：AI 理解意图，日历 API 完成真实占用

候选阶段：解析日期/时间/参会人/会议室 → 解析重名 → 查人员忙闲 → 查会议室忙闲 → 返回最多 3 个候选
确认阶段：领取 action → Redis 房间时段锁 → 再查全部忙闲 → 创建临时日程 → 邀请会议室 → 等待 RSVP
完成阶段：会议室 accept → 添加申请人和参会人 → 保存预约 → 创建会后提醒 → 返回结果卡片

会议室同步和筛选

Worker 每 15 分钟同步会议室名称、容量、层级、启用状态、禁用区间和预订限制；状态变化事件会触发刷新。候选只包含启用、未禁用、容量足够、时长合规且不需要审批的普通会议室。忙闲不依赖缓存，候选和最终确认都会实时查询飞书。

参会人解析为什么不能猜

系统使用通讯录把姓名解析成 open_id，再批量查询忙闲。重名或未匹配必须让用户选择。错误地把“王伟”解析成另一个人不仅会造成冲突判断错误，还可能泄露他人忙闲。

候选算法

申请人计入参会人数；未指定容量时优先选择刚好容纳人数的最小房间，减少大会议室浪费。人员忙闲按飞书接口限制分批查询，会议室忙闲也分批查询；在指定当天、工作时间内按 30 分钟粒度寻找交集，最多返回 3 个候选。

为什么确认时必须再次查询

用户看到候选到点击确认之间存在竞态，房间或参会人可能已被其他系统占用。候选仅在 15 分钟内有效，确认时先用 Redis 锁住“房间 + 时间段”，再向飞书实时复核。锁只解决本系统内部竞争，飞书复核解决外部竞争。

为什么创建日程要分步骤并补偿

  1. 在应用专用共享日历创建临时日程。
  2. 先添加资源类型会议室并检查 RSVP。
  3. 会议室接受后再添加申请人和其他参会人。
  4. 任一步失败就删除临时日程；清理失败标记 needs_admin 并告警。

飞书日历不是本地数据库事务，不能使用一次 SQL rollback。这里采用 Saga/补偿思想：每个外部步骤都有反向清理动作。相比“先邀请所有人再看房间是否成功”，它能减少幽灵日程和误通知。

取消、改期和会后归还提醒

用户只能操作自己经行政 AI 创建的预约。取消删除飞书日程并取消本地投递；改期采用“先创建新预约，成功后删除旧预约”，新方案失败时保留原日程。预约成功时创建一条结束时间投递，Worker 到点私聊组织者关闭设备、带走物品并恢复会议室；取消和改期会同步处理投递。

这条链路的核心不是 NLP，而是资源一致性：模型只负责把话变成字段，真正的占用结果以飞书会议室 RSVP 和日程事件为准。

十七、Agent 与模型配置：把模型当可替换供应商

行政助手和生图 Agent 都有独立 agent_key、显示信息、模型、启用状态、凭证来源和设置。阿里云生成、Embedding、Rerank、上下文模型也分别配置，避免“一把模型包办所有任务”。

Generation

负责最终制度回答，偏重中文生成质量和遵循引用指令。

Embedding

把问题和制度切片变为向量，关注语义检索质量和成本。

Rerank

对较少候选做精排，关注相关性而不是语言生成。

Context model

输出结构化意图和独立问题，默认使用更便宜、更快的模型。

Image model

由中转站和协议决定能力，独立于行政助手文本模型。

Demo provider

未配置真实密钥时提供确定性结果，方便开发 UI 和测试，但不能用于生产答案。

为什么使用 Provider/Adapter 接口

业务层只调用 Generate、StreamGenerate、Embed、Rerank 等能力，不直接依赖供应商 JSON。这样更换模型只影响适配器与配置；权限、引用、会话和审计逻辑保持不变。

配置为什么需要版本

Prompt、温度、召回数、阈值和模型改变都可能影响答案。草稿—发布模式让线上始终只有一个明确版本，并可在审计中回答“这条回答用了哪套配置”。相比直接覆盖一行配置，它更适合企业问题追踪和回滚。

十八、AI 生图 Agent：多中转站、项目权限和异步任务

中转站与模型

后台内置 XGAPI 和 Comfly 的 API Base URL，管理员填写各自 API Key、连接超时和允许的图片响应域名；通过 /models 同步模型后，再明确启用支持生图的模型，并配置 Chat Completions 或 Images Generations 协议、参考图、反推、1K/2K/4K 与最大数量能力。

模型列表“能看到”不等于“能生图”，因此同步后默认不直接开放。能力由管理员显式声明，员工端只显示已启用且有项目权限的组合。

为什么不自动切换中转站

中转站不是无差别节点：费用、账号额度、模型版本和数据发送边界都不同。自动故障切换虽然看似提高可用性，却可能把公司图片发送给管理员未选择的供应商。因此当前失败只按同一中转站重试，不跨站切换。

项目 ACL

每个公司项目可以面向全员、指定飞书部门或指定人员开放。停用项目后禁止新任务，但保留历史画布只读。权限在服务端检查，图片资源接口也检查资产所属项目和用户，不能通过猜资产 ID 跨项目查看。

参考图与图片反推

  • 支持 JPG、PNG、WEBP；单张最多 10 MB，最多 5 张，总计最多 30 MB。
  • 本地上传先查毒并存 MinIO；画布已有图片可通过拖拽资产 ID 复用，不重复上传。
  • 图片反推固定走多模态 Chat，只接受文本描述，不生成图片。

快捷功能与卡通化强度

功能按键由管理员配置，可全局或项目级覆盖。普通模板点击后可立即发起生成；若包含一次 "cartoonization_strength": 0，前端显示 0、0.25、0.5、0.75、1 五档滑块并实时替换字段，必须再点“生成图片”。后端保存时再次校验字段只能出现一次且范围为 0～1。

异步生图与部分成功

1/2/4/8 张会拆为独立输出请求，同一任务最多并发两个。Worker 领取任务后根据协议组装请求，解析 Base64、Data URL、Chat 图片块、Markdown 图片链接或 HTTPS URL。网络、429 和 5xx 最多退避重试三次；部分图片成功时保留结果并标记 partial，而不是全部作废。

为什么生图必须异步

4K 图片和多张生成可能耗时很长，HTTP 请求容易超时。先创建任务和占位节点，页面轮询任务状态，Worker 完成后原位替换，可在刷新后恢复，也能记录每个输出的成功与失败。

远程图片 URL 为什么要白名单

中转站可能返回自己的 CDN 地址。服务端下载前检查 HTTPS、允许域名、DNS 解析不能指向私网、重定向仍需通过检查、MIME 必须是图片且不超过 64 MB，最后再查毒。这样防止上游响应诱导服务器访问内网地址，即 SSRF。

允许输出域名不是“越多越好”。应只添加真实中转站或其 CDN 域名；通配整个公共云域会显著扩大 SSRF 与恶意内容下载面。

十九、无限画布：Vue Flow 把图片变成有坐标的持久节点

每位用户在每个授权项目下只有一张私人画布。画布保存视口 x/y/zoom 和节点的 x/y/width/height/z-index。新任务在当前视野中心按网格创建占位节点，生成成功后节点保持位置只替换资产，失败则显示错误状态。

为什么选 Vue Flow，而不是自己监听鼠标事件

无限画布需要处理屏幕坐标与世界坐标转换、缩放中心、拖动、平移、节点选择、视口、小地图和触控边界。手写首版看似简单，但容易出现缩放后拖动偏移、MiniMap 视野不一致和高 DPI 问题。Vue Flow 已提供成熟的空间模型，项目只需实现图片节点和持久化。

拖拽到参考图

图片节点提供专用拖拽手柄，在 dataTransfer 中写入资产 ID；参考图槽位处理 drop 后读取资产并加入列表。使用资产 ID 而不是图片 URL，能让后端重新校验权限，也避免复制临时鉴权 URL。

右下角 MiniMap

MiniMap 显示所有节点和当前视野遮罩，支持拖动、缩放和点击定位。点击地图坐标后调用画布的 setCenter，再保存新的视口。地图是空间导航器，不只是静态缩略图。

为什么画布保存版本号

两个浏览器标签可能同时编辑同一画布。如果只做“最后写入覆盖”，晚提交的旧页面会悄悄抹掉新节点。乐观版本号要求 PATCH 携带读取时版本；冲突时重新加载服务器最新版，让冲突可见。

恶意文件格式/大小限制、ClamAV、鉴权资源接口降低解析漏洞和公开对象地址风险
SSRF输出域名白名单、DNS 私网检查、重定向复检防止中转站诱导服务器访问内网
错误外部操作提醒/会议/通知确认，服务端最终校验模型理解不等于获得执行授权

为什么后台 API Key 要加密而不只是脱敏

脱敏只影响展示，数据库中若仍是明文，备份泄露或只读数据库账号被攻破仍会暴露密钥。项目用由 AGENT_SECRET_ENCRYPTION_KEY 派生的 AES-GCM 密钥加密，兼顾保密和完整性。更高等级环境可替换为 KMS/Vault，使应用数据库也无法独立解密。

为什么不能把前端校验当安全措施

前端的时间范围、图片数量、项目选择和按钮禁用都可以被修改请求绕过，所以后端必须重复校验。前端校验用于即时反馈，后端校验用于建立可信边界。

二十一、部署与网络：Docker Compose + Nginx 的现实平衡

Compose 启动 PostgreSQL、Redis、MinIO、Tika、ClamAV、API、Worker 和 Web。Nginx 提供静态 Vue 页面，并把 /api/ 代理到内部 API；数据库、Redis、Tika 和 API 默认不直接暴露公网。

Nginx 的关键配置

  • proxy_buffering off：保证 SSE 增量及时到达。
  • try_files ... /index.html：支持 Vue history 路由刷新。
  • /assets/ 使用长期 immutable 缓存；index.html 禁止长期缓存。
  • 资源 chunk 不存在时返回 404，不误返回 HTML，避免飞书 WebView 把 HTML 当 JavaScript 执行。
  • 当前宿主端口绑定 127.0.0.1:8088，避免意外暴露到所有网卡；生产应由 HTTPS 网关转发。

为什么现在不使用 Kubernetes

Kubernetes 解决的是多节点调度、弹性、自愈、滚动发布和复杂网络治理。当前 1～2 台服务器用 Compose 更容易备份、排查和交接。若 API/Worker 需要独立弹性扩容、多环境频繁发布或高可用跨节点，才进入 K8s 的收益区间。

迁移文件的注意点

/docker-entrypoint-initdb.d 只在全新 PostgreSQL 数据卷执行。已有环境升级必须显式执行新增迁移，不能认为“重启容器就会自动升级”。生产进一步应引入正式 migration runner 和版本表。

二十二、测试与可观测性：测试确定性边界，不测试模型“心情”

后端测试重点

  • ACL 对部门、职位、人员和显式权限键的允许范围。
  • 引用缺失、越界和撤权历史不能继续使用。
  • 上下文补全、主题切换、重置和模型失败降级。
  • 提醒解析、工作日、任务租约、重试与幂等。
  • 会议室候选、并发确认、RSVP、补偿、取消、改期和会后投递。
  • 中转站协议、密钥加密、SSRF、任务部分成功和画布版本冲突。

前端测试重点

Vitest + Vue Test Utils 验证路由权限、H5 登录回退、通知 Markdown、表单和组件交互；Playwright 验证真实浏览器中的登录、流式聊天、管理页面和画布操作。模型接口应使用可控 mock，真实中转站只做少量验收测试，避免费用和随机性让测试不稳定。

指标和审计

系统记录登录、权限修改、IAM同步与降级、资料上传与发布、ACL 修改、配置发布、通知审批发送、会议预约和生图调用。质量看板关注问题数、已发布文档等基础指标；建议持续补充首字延迟、完整耗时、无答案率、引用覆盖率、模型费用、同步积压、飞书发送成功率和生图失败原因分布。

端到端成功率不能只看 HTTP 200。例如会议室必须看 RSVP 是否 accept，通知要看每个接收者投递结果，生图要看输出资产是否完成校验并落入 MinIO。

二十三、当前实现边界与应补强点

领域当前边界建议触发条件
OCR没有独立 PaddleOCR 流程扫描 PDF 命中率明显偏低时加入 OCR 与版面分析
检索融合加权混合 + 词命中重排，不是严格 RRF评测显示某类问题被应用层词筛选误伤时升级
数据库迁移新增迁移需人工对已有数据卷执行进入多人持续部署前引入 migration runner
高可用Compose 主要面向单机/双机出现明确 RTO/RPO 和跨节点容灾要求时升级
生图工作流只有入口占位明确节点类型、输入输出契约和版本规则后再建设
生图协作每用户、每项目私人画布出现多人实时编辑需求时引入操作日志/CRDT
密钥管理应用层 AES-GCM合规要求密钥托管、轮换或审计时接 KMS/Vault
审批会议室只自动预约无需审批的普通会议室飞书开放适合应用身份的审批闭环后再接入

“边界”不是缺陷清单，而是有意控制首期复杂度。是否补强应由评测、容量、合规和真实业务频率驱动，而不是为了追求技术名词齐全。

二十四、什么时候应该换成其他方案

什么时候从 pgvector 迁移独立向量数据库？
当有效切片达到千万级、向量检索 QPS 明显挤压主库、需要多向量字段/高级过滤或跨地域索引时。迁移前应先做索引、查询计划和真实召回评测，不能只看文档数量。
什么时候引入 Kafka、RabbitMQ 或专用任务队列？
当任务吞吐远高于业务事务、需要多消费者广播、严格顺序分区或跨服务事件流时。当前数据库任务队列具备持久化、行锁和审计，规模较小时更简单。
什么时候拆微服务？
当会议、生图、知识解析拥有独立团队和发布节奏，资源模型差异巨大，或某模块故障频繁影响其他模块时。拆分应沿已有模块边界进行，而不是按数据库表随意拆。
什么时候改用 WebSocket 传 AI 回答？
当同一浏览器连接需要双向实时协作、服务器主动推送多个频道、画布多人编辑或语音流时。单向文本生成继续使用 SSE 更简单。
什么时候使用本地大模型？
当制度片段不允许离开内网、调用量足以摊薄 GPU 成本，且团队具备模型推理运维能力时。Provider 抽象允许替换模型，但本地化还需要评测、容量和安全治理。
什么时候升级 Kubernetes？
当多节点高可用、自动扩缩容、滚动发布、资源配额和多环境治理成为持续痛点时；不是因为容器数量超过几个就必须升级。

二十五、核心设计原则总结

  1. 模型负责理解，代码负责授权。
    AI 输出不能扩大 ACL、决定权限或绕过确认。
  2. 先持久化，再异步执行。
    提醒、通知、会议投递和生图都必须能从重启中恢复。
  3. 候选不是结果。
    会议室在确认时复核，外部 RSVP 才是真实成功。
  4. 历史不是证据。
    制度问答每轮重新检索，引用只来自本轮授权片段。
  5. 前端校验改善体验，后端校验建立安全。
    任何可修改请求都必须在服务端重验。
  6. 所有外部副作用都要幂等。
    飞书事件、卡片点击、消息发送和 Worker 都可能重复。
  7. 外部事务使用补偿。
    日历、消息和模型调用不能依赖数据库 rollback。
  8. 架构随证据演进。
    当前规模优先可维护性，达到容量或组织触发点再拆分。
一句话概括：这套系统的技术价值不在于“接了几个大模型”，而在于把不确定的模型能力包在身份、权限、证据、确认、幂等、补偿和审计这些确定性工程边界之内。
